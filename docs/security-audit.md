# Аудит безопасности админ-панели (06.10.2026)

Документ для владельца сайта и разработчика. План дальнейших улучшений — [admin-roadmap.md](admin-roadmap.md), инструкция для персонала — [posibnyk-administratora.md](posibnyk-administratora.md). Предыдущие версии аудита и планов удалены: после них проект сильно изменился (двуязычность, зеркалирование файлов, карточки документов), аудит выполнен заново по текущему коду.

Файл хранится в репозитории: находки высокого уровня исправлены в той же правке и закреплены тестами; независимая проверка (раздел 8) выявила обходы первой версии санитайзера, после чего он заменён DOM-библиотекой. Повторная независимая проверка текущего рабочего дерева (раздел 9) выявила незакрытые границы: старый HTML, независимый запуск деплоя и неподтверждённую защиту файлов на хостинге. Статус «исправлено в коде» не означает подтверждённую безопасность развёрнутого сайта.

## 1. Резюме

Админка — панель Filament 3 по адресу `/admin`. До аудита базовая гигиена уже была: CSRF на всех формах, bcrypt-хэши, серверные сессии в БД, нет саморегистрации и сброса пароля, лимит 5 попыток входа в минуту на IP, HTTPS и HSTS, document root хостинга — `public/` (`.env`, `.git`, `vendor/` снаружи недоступны).

Главная проблема была не в «дырке», а в **отсутствии глубины защиты**: любая учётка была суперадмином, любой файл можно было загрузить в публичный каталог, зависимости содержали 27 известных уязвимостей, а защитные заголовки не доходили до `/admin`. Компрометация одного пароля сотрудника (фишинг, подбор, заражённый компьютер) означала полный контроль над сайтом.

В коде реализованы основные меры высокого приоритета и часть среднего. Границы старого контента, приёмка на хостинге и цепочка деплоя остаются открытыми (раздел 9):

## 4. Что уже было хорошо (подтверждено)

- Аутентификация только через Filament Login; `/admin/register` и `/admin/forgot-password` — 404 (тест `AdminExposureTest`).
- Пароли — bcrypt (`'password' => 'hashed'`); `AuthenticateSession` разлогинивает другие устройства при смене пароля; сессии в БД.
- CSRF на всех POST, в т.ч. Livewire; `APP_DEBUG=false` в прод-шаблоне.
- Document root хостинга — `public/`: `/.env` → 404, листинг `/storage/` → 403.
- `DocumentResource` уже ограничивал MIME (PDF/DOC/XLS) и размер.
- Превью черновиков и несохранённых форм — только для залогиненных (`abort_unless(auth()->check(), 404)`); снимок формы живёт 10 минут в кэше под случайным токеном.
- Зеркалирование файлов старого сайта — белый список хостов, расширений и проверка сигнатур (`otfk:mirror-files`).
- `TelegramPoster` обращается к `api.telegram.org`; проверка паролей в production также обращается к `api.pwnedpasswords.com` (см. С2). `LinkChecker` работает по БД и диску, без запросов наружу.
- `robots.txt` закрывает `/admin` и `/livewire`; админка не попадает в статистику визитов.
- На тестовом хостинге одна учётка; дефолтный пароль сидера не используется; токен Telegram пуст.

## 5. Находки подробно

### В1. Нет ролей и политик доступа — исправлено

- **Было:** `User::canAccessPanel()` всегда `true`, Policies отсутствуют; `UserResource` доступен каждому — любой сотрудник создавал и удалял администраторов.
- **Стало:** колонка `users.role` (`admin`|`editor`, миграция `2026_10_06_220000`; все существующие пользователи стали `admin`, новые по умолчанию `editor`). `UserPolicy`, `SettingPolicy`, `MenuItemPolicy` (наследуют `AdminOnlyPolicy`) и `canAccess()` на `UserResource`, `SettingResource`, `MenuItemResource` и базе страниц настроек `SettingsFormPage` (плюс повторная проверка в `save()` и `sendTest()` на случай смены роли после открытия страницы). Редактор получает 403 и не видит эти разделы в меню. `User::booted()` запрещает удалить себя, удалить или понизить последнего администратора, принять неизвестную роль. Поле «Роль» в форме; собственная роль недоступна для редактирования. Массовое удаление пользователей выключено.
- **Границы:** редактору доступны все контентные разделы, включая «Плитки на головній», «Банери», «Оголошення» нет (это страница настроек), «Розклад дзвінків» (пишет настройки `bells_*` напрямую, без политики — осознанно).
- **Тест:** `AdminRolesTest`.

### В2. Загрузка файлов любого типа в публичный каталог — исправлено

- **Было:** вложения RichEditor (страницы, новости, спеціальності, підрозділи) сохранялись в `/storage/<dir>` под именем `hashName()` с расширением, угаданным **по содержимому** (`<?php` → `.php`); `ProgramResource` принимал любой файл с клиентским расширением; `->image()` принимал SVG. Исполнение PHP в `/storage/` на хостинге не было проверено.
- **Стало, три слоя:**
  1. `config/livewire.php` опубликован: единые серверные правила временной загрузки для всех форм — `extensions:` (jpg/png/gif/webp/pdf/doc(x)/xls(x)/ppt(x)/odt/ods/odp) **и** `mimetypes:` по фактическому содержимому (fileinfo), `max:20480`; `svg` убран из `preview_mimes`. PHP под именем `photo.jpg` отклоняется по MIME.
  2. `ProgramResource` — `acceptedFileTypes` PDF/DOC/DOCX и `maxSize(20480)`; `DocumentResource` уже был ограничен.
  3. `storage/app/public/.htaccess` (теперь в git, `!.htaccess` в `.gitignore` каталога): запрет `.php|.phtml|.phar|.pl|.py|.cgi|.sh|.shtml` (`Require all denied` под `IfModule mod_authz_core`, иначе `Deny from all`), `php_flag engine off` под `IfModule mod_php*`, `X-Content-Type-Options: nosniff`, для `.html|.svg|.xml|.js` — `Content-Security-Policy: sandbox allow-scripts allow-popups` (скрипт в таком файле исполняется в изолированном origin без cookie и без доступа к `/livewire`). Каждая директива под `IfModule`, чтобы отсутствие модуля не дало 500; остаётся риск `AllowOverride` без `AuthConfig`/`FileInfo` — проверяется чек-листом. На ukraine.com.ua статику может отдавать nginx напрямую: тогда заголовки из `.htaccess` не применяются, но и PHP в `/storage/` не исполняется (к Apache проксируются только `.php`). Файлы с опасными расширениями через формы больше не загружаются, но каталог `mirror/` старого сайта может их содержать.
- **Побочный эффект:** favicon/логотип теперь только PNG/JPG/WebP (загрузка SVG и ICO отклоняется; ранее загруженные файлы продолжают работать).
- **Требует проверки на хостинге** (раздел 6): что `.htaccess` читается без ошибки 500 и что скрипт в `/storage/` не исполняется.
- **Тест:** `AdminSecurityTest::test_livewire_upload_rules…`, `…test_uploads_directory_forbids_script_execution`.

### В3. Уязвимые зависимости — исправлено

- **Было:** `composer audit` — 27 advisories в 7 пакетах: `filament/forms` (CVE-2026-55409, XSS через RichEditor, ≤ 3.3.52), `guzzlehttp/guzzle` ×9, `guzzlehttp/psr7` ×2, `league/commonmark` ×12, `livewire/livewire`, `laravel/framework`, `league/flysystem`. В CI шаг с `continue-on-error`.
- **Стало:** `composer config platform.php 8.3.0` (lock устанавливается на PHP хостинга), обновление без понижений: Filament 3.3.52 → 3.3.56, Laravel 12.61.1 → 12.69.3, Livewire 3.8.1 → 3.8.10, Guzzle 7.11 → 7.15.5, psr7 2.11 → 2.13.1, CommonMark 2.8.2 → 2.10.3, Flysystem 3.34 → 3.36, Symfony 7.4.x патчи. `composer audit` — 0. В `tests.yml` шаг стал блокирующим (`composer audit --no-interaction --locked`).
- **Регламент:** ежемесячно `composer audit`, `composer outdated --direct`, `npm audit`; обновления только патч/минор под `platform.php`.

### В4. Защитные заголовки не применяются к `/admin` — исправлено

- **Было:** `SecurityHeaders` только в группе `web`; маршруты Filament регистрируются со стеком панели — подтверждено `curl -I https://just-test.shop/admin/login` (ни одного защитного заголовка).
- **Стало:** `SecurityHeaders` добавлен в `->middleware([...])` панели; во все ответы добавлен `Content-Security-Policy: frame-ancestors 'self'`; для `/admin*`, `/admin-preview/*`, `/livewire/*` — `X-Robots-Tag: noindex, nofollow`.
- **Тест:** `AdminSecurityTest::test_admin_pages_get_security_headers_and_noindex`.

### В5. Stored XSS через контент и ссылки — новые записи защищены, старые требуют проверки

- **Было:** HTML редактора выводится через `{!! !!}` без очистки; JSON-LD в `breadcrumbs.blade.php` и `news/show.blade.php` без `JSON_HEX_TAG` (заголовок `</script><script>…` разрывал скрипт); поля URL меню/плиток/баннеров/оголошення принимали `javascript:`. До ролей это считалось допустимым («контент админский»); с ролью редактора это путь эскалации до администратора и атака на посетителей.
- **Стало:** каст `App\Casts\SafeHtml` (→ `App\Support\HtmlSanitizer`) на `body`/`body_en` страниц и новостей, `description`/`description_en` спеціальностей и підрозділів, `bio`/`bio_en` персонала — применяется при записи атрибута, то есть и для Filament, и для `saveQuietly()`/импортов. Движок — `symfony/html-sanitizer` (DOM-парсер, белый список W3C Sanitizer API, явно добавлен в `composer.json`): остаются текстовая разметка, списки, таблицы, native `<details>`, изображения (`http(s)`/относительные/`data:image`), ссылки `http(s)/mailto/tel`/относительные, атрибуты `class/id/style/title/alt` и оформление таблиц; `<iframe>` — только по белому списку `App\Support\Sanitizer\IframeSourceSanitizer` (`youtube.com/embed`, `youtube-nocookie.com/embed`, `google.com/maps`, `docs.google.com/(document|presentation|spreadsheets)`, `drive.google.com/file`, относительные `/storage/...`; `sites.google.com` и Google Forms — нет, это готовые фишинговые страницы). Удаляется всё остальное: `<script>`, `<style>`, `<object>`, `<embed>`, обработчики `on*`, `srcdoc`, `javascript:`/`vbscript:`-URL. Текст с «голым» `<` (`a < b`) экранируется, а не превращается в тег; невалидный UTF-8 нормализуется, а не пропускается. Парсер отбрасывает комментарии, поэтому маркеры `<!--imported-from:…-->` сохраняются отдельно и дописываются в конец (как в оригинале — с переносом строки или без). Уже сохранённый контент не переписывается — очистится при следующем сохранении записи. `JSON_HEX_TAG` добавлен во все JSON-LD. Правило `App\Rules\SafeUrl` на URL меню, плиток, баннеров, оголошення и значениях `type=url` в «Розширені налаштування».
- **История:** первая версия на регулярных выражениях была отклонена независимой проверкой (обходы `<img/src=x onerror>`, `<scr<script>ipt>`, fail-open на невалидном UTF-8, порча текста с `<`) — см. раздел 8; тест `AdminSecurityTest` теперь содержит эти пейлоады.
- **Побочный эффект:** санитайзер нормализует разметку при сохранении (самозакрывающиеся `<img />`, `<tbody>` в таблицах, кавычки у атрибутов; `&#61;`/`&#64;` парсера декодируются обратно в `=`/`@`) — на отображение не влияет; тесты «точного сохранения HTML» (`ContentTranslationTest`, `AcademicTranslationTest`, `LocalizationNavigationTest`) переведены на нормализованный ожидаемый HTML. `translation_source_hash` после первого пересохранения старого материала будет пересчитан.
- **Остаток:** `map_embed` выводится в `src` iframe экранированным (не XSS-сток), но без allowlist origin — осталось в плане.
- **Тест:** `AdminSecurityTest::test_rich_text_is_sanitized…`, `…test_json_ld_escapes…`, `…test_link_fields_reject_dangerous_schemes`.

### С1. Нет второго фактора — план

Фишинг остаётся самым вероятным сценарием. Решение — TOTP (Google Authenticator/Aegis) обязательный для роли `admin`, желательный для `editor`; варианты — `jeffgreco13/filament-breezy ^2` для Filament 3 или собственная реализация. Детали — этап 2 roadmap.

### С2. Политика паролей и смена без подтверждения — частично исправлено

- **Исправлено:** `Password::defaults()` в `AppServiceProvider` (12+ символов, буквы и цифры, в production `uncompromised()` — синхронный запрос к api.pwnedpasswords.com при создании пользователя/смене пароля; при недоступности сервиса проверка пропускается, при медленном исходящем канале форма может задержаться на несколько секунд); `UserResource` использует `Password::default()`; страница профиля Filament применяет его автоматически.
- **Осталось:** профиль Filament позволяет сменить e-mail и пароль без ввода текущего пароля — украденная сессия превращается в постоянный доступ. План: собственная страница профиля с полем «текущий пароль» (этап 2).

### С3. Журнал безопасности — частично исправлено

- **Исправлено:** `App\Listeners\LogAuthenticationEvents` (event discovery) пишет `auth.login`/`auth.failed`/`auth.logout`, а собственная страница входа `App\Filament\Auth\Login` — `auth.lockout` (Filament использует `danharrin/livewire-rate-limiting`, который не шлёт событие `Lockout`) в канал `security` (`storage/logs/security-YYYY-MM-DD.log`, уровень `info` фиксирован, 90 дней) — только e-mail, IP, User-Agent, без паролей. `users.last_login_at`/`last_login_ip` обновляются при входе и показаны в таблице «Користувачі».

### С5. Дефолтные реквизиты в сидере — исправлено

`DatabaseSeeder` выбрасывает исключение, если `ADMIN_PASSWORD` пуст вне окружений `local`/`testing`; использует `firstOrCreate` (повторный сидер не перезаписывает пароль) и назначает роль `admin`. `DEPLOY.md` больше не предлагает входить под `password`. ### С6. Деплой: push в `master` = прод — частично исправлено

- **Было:** `deploy.yml` стартовал на push независимо от `tests.yml`; сервер делал `git reset --hard origin/master`, то есть мог получить ревизию новее той, для которой собран фронтенд.

- **Осталось (процесс):** branch protection (PR-only, required check, запрет force-push), обязательная 2FA в GitHub у всех с правом записи — этап 1 roadmap.

### С7. Резервные копии — план

`otfk:backup` складывает дампы на тот же хостинг (`storage/app/backups`, 14 копий). При компрометации хостинга копии теряются вместе с сайтом. Нужна внешняя копия БД **и файлов с одинаковым RPO** (ежедневный дамп + ежедневная инкрементальная синхронизация `storage/app/public`, иначе восстановленная БД ссылается на отсутствующие вложения), независимые ключи, защита от удаления, оповещение о просроченной копии и репетиция восстановления БД+файлов в изолированном окружении без Telegram — этап 3.

### Н1. «Запам'ятай мене»

Remember-cookie Laravel живёт 400 дней; на общем компьютере это постоянный доступ. План: сократить до 30 дней (`auth.guards.web.remember = 43200` до создания guard либо `SessionGuard::setRememberDuration(43200)`; верхнеуровневый `auth.remember` не используется) или убрать флажок для роли `admin` — этап 2. Пока — правило для персонала в инструкции.

### Н2. CSP

Полный CSP с nonce сломает Livewire/Alpine/Filament; ограничиваемся `frame-ancestors`. Не планируется без отдельной задачи.

### Н3. `robots.txt` и путь `/admin`

`Disallow: /admin` стандартен для любого Laravel/Filament-сайта; путь легко угадывается, поэтому защита строится не на его скрытии. Публичная ссылка убрана, индексация запрещена заголовком — этого достаточно.

- Новый Resource или Page Filament — сразу решить роль: контент → доступно редактору; настройки/структура/пользователи → `canAccess()` + Policy наследник `AdminOnlyPolicy` + тест.

## 9. Повторная независимая критика рабочего дерева (06.10.2026)

Проверены текущие незакоммиченные изменения, код приложения, vendor и workflows. Запущены `AdminRolesTest`, `AdminSecurityTest`, `AdminExposureTest`: **20 passed, 271 assertions** в SQLite `:memory:`; production config cache отсутствовал. Выполнены локальные пробы санитайзера без записи в БД. Хостинг, настройки GitHub и актуальная база advisories в этой проверке не проверялись. Результаты предыдущего аудита не выдаются за новые измерения.

1. **Высокий приоритет: CI не является шлюзом деплоя.** `.github/workflows/deploy.yml` независимо стартует на push и вручную, без зависимости от успешного PHP-теста и аудита. Кроме того, ассеты относятся к checkout запуска, а PHP-код — к текущему `origin/master`: следующий push может дать разные ревизии. Нужны проверка успешного CI для конкретного SHA и установка этого же SHA на сервер; branch protection дополняет, но не заменяет этот контракт.
2. **Высокий приоритет до закрытия В5: старый HTML не защищён новым кастом.** `SafeHtml::get()` возвращает сохранённый текст без очистки; локальная проба сохранила `<img src=x onerror="alert(1)">` при чтении. Это доказательство границы, а не утверждение о заражённой БД. Нужны инвентаризация обеих локалей и старых URL, резервная копия, отчёт dry-run и контролируемая очистка с проверкой ссылок/переводов. Прямые SQL/Query Builder обновления также обходят касты. Нельзя массово пересохранять новости без учёта Telegram observer.
3. **Высокий приоритет приёмки: защита storage пока не подтверждена сервером.** Тест `test_uploads_directory_forbids_script_execution` проверяет строки `.htaccess`, не выполнение запретов. Статический PDF с HTTP 200 и `IfModule` не доказывают работоспособность защиты. Закрывать В2 следует после проверки реального веб-сервера, запрета исполнения и изоляции старых активных файлов. Отрицательных результатов проверки хостинга в этой ревизии нет: она не выполнялась.
4. **Средний приоритет: план 2FA мог создать слепую зону тестов.** Глобальный обход через `runningUnitTests()` исключил бы реальный барьер из Feature-тестов. Нужны тесты без подтверждённого фактора для прямых URL и Livewire, неверного/повторного кода, rate limit, recovery codes, отключения/сброса фактора и remember-сессии. Подтверждённый фактор задаётся только фикстурам контентных тестов. Для редакторов с правом публикации риск фишинга остаётся существенным; опциональность 2FA — решение владельца с принятием этого риска.
5. **Средний приоритет: критерий внешнего бэкапа неполон.** Ежедневная БД и ежемесячные файлы допускают потерю почти месяца загрузок; восстановленная БД может ссылаться на отсутствующие файлы. Нужны отдельные RPO/RTO для БД и storage, достаточно частое копирование файлов, независимые ключи восстановления, ретенция/защита от удаления и оповещение о просроченной копии. Репетиция должна включать БД и файлы в изолированном окружении без отправки Telegram.
6. **Средний остаточный риск: санитайзер не предотвращает подмену интерфейса CSS.** Локально `HtmlSanitizer::clean()` сохранил `style="position:fixed;inset:0;z-index:2147483647;background:white"`. Это не доказанный JavaScript-XSS, но редактор может перекрыть страницу произвольным содержимым. Решение — ограничить допустимые CSS-свойства с проверкой импортированной разметки либо явно принять риск от роли издателя; запрет Google Forms сам по себе не устраняет фишинг через контент.

Дополнительные исправления точности: установленный `SessionGuard` задаёт **576000 минут = 400 дней**, не пять лет; `AuthManager` читает `remember` из конфигурации guard, не из `auth.remember`. Проверка отсутствия известных уязвимостей — результат на дату запуска, а не постоянное свойство проекта.

Вывод: базовые меры полезны и профильные тесты зелёные, но формулировка «все высокие риски закрыты» преждевременна. Сначала завершить приёмку storage, старого контента и цепочки деплоя; затем подтверждение чувствительных действий, 2FA и восстановление. Оценки этапов считать предварительными до проверки совместимости 2FA и возможностей внешнего хранилища.

Авария, исключение или нехватка памяти оставят частично очищенную БД без копии. Результат записи файла не проверяется; старый `translation_source_hash` и выбранное соединение в копию не включены. До использования `--apply` нужны надёжно записанный и проверенный бэкап до первой мутации (либо журнал перед каждой записью), необходимые метаданные восстановления и тест отказа записи/прерывания. Один успешный тест не проверяет эту гарантию.
2. **P1 — «только нормализация» не является доказательством безопасности.** Прямой вызов `removedMarkup()` для `<img/src=x onerror=alert(1)>` возвращает пустой список, хотя DOM-санитайзер удаляет `onerror`. Для `style="position:fixed;color:red"` удаление `position` также классифицируется как нормализация: имена атрибутов не изменились. Сам санитайзер в первой пробе защиту выполняет; дефект находится в отчёте и выводах о старой БД. Нужен полный структурный diff, учитывающий значения, либо честный статус «изменено, требует проверки» для неклассифицированных различий. Требуется повторная оценка старого контента; эта проверка не утверждает, что БД заражена. Команда также не инвентаризирует старые URL меню/баннеров/плиток/настроек, ранее охваченные замечанием 9.2.
3. **P2 — CSS-перекрытие сохраняется через `class`.** `HtmlSanitizer::clean('<div class="fixed inset-0 z-50 bg-white">Fake login</div>')` возвращает строку без изменений. Фильтр inline `style` устраняет конкретную пробу, но не заявленный риск подмены интерфейса. Нужна политика разрешённых классов контента/изоляция оформления и регрессионный тест либо явное принятие риска издателя. Это CSS-подмена, не доказанный JavaScript-XSS.

- **Защита от самоблокировки (требование владельца):** 10 одноразовых кодов восстановления (показываются один раз, регенерация по текущему коду); кнопка «Скинути 2FA» у администратора для других пользователей (не для себя); команда `otfk:two-factor {email} --reset` и `--status` по SSH; аварийный выключатель `TWO_FACTOR_ENFORCE=false` в `.env`. Последний администратор не может сбросить себе фактор через UI — остаются коды, консоль и выключатель. Все пути проверены `TwoFactorTest`.
- **Тесты:** принуждение в тестах не отключается; `TestCase::actingAs()` задаёт фикстурный подтверждённый фактор и отметку сессии только как фикстуру, а `TwoFactorTest` входит через `actingAsWithoutTwoFactor()` и проверяет редиректы, Livewire-403, неверный/повторный код, одноразовость recovery-кодов, сброс, выключатель, регенерацию и переподключение.
- **Остаток:** «Запам'ятай мене» и смена пароля/почты без текущего пароля — этап 2 roadmap; доверенные устройства (пропуск кода на 30 дней) не реализованы намеренно: код вводится при каждом входе.
